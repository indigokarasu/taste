# Gotchas — full incident list

When to read: before a scan, Styx delta, enrichment run, or dispatch-triggered scan; when a run reports success but the data looks wrong; when debugging token, dedup, backfill, or schema problems. These are the non-obvious failure modes distilled from real incidents — each entry is a rule, not a story.

- **Empty or corrupt token file (0 bytes)** — If the token file is empty or 0 bytes, `json.loads()` fails with "Expecting value: line 1 column 1". The `google_auth.py` helper skips that account and silently falls back to the next account in the list (the agent's), which has zero consumption emails. The scan then reports 0 messages across all services with no obvious error. **Diagnosis:** Check file size with `wc -c` on the token file before assuming auth is valid. **Fix:** Re-authorize with the same procedure as `invalid_grant`.
- **Scripts may fall back silently** — When a token is invalid or 0 bytes, standalone auth helpers may silently fall back to a different account. Always verify which account was actually loaded.
- **A merchant-alias join multiplies one purchase into N Styx rows — dedup by `transaction_id`, not merchant name (confirmed 2026-09-26)** — `transaction_merchants` maps ONE Plaid `transaction_id` to MULTIPLE `merchants` rows when Plaid renames a merchant. Confirmed: transaction `4ooKNoadqPTN3eLDXY4nFx5ZErYxXDHD91Rd0` ($11.70, 2026-06-15) was linked to both `Berkeley Bowl` and `Berkeley Bowl West`, so the same single purchase appeared as two candidate rows. A name-based merchant check sees the second alias as "new" and writes a duplicate signal. **Rule:** key the dedup on `transaction_id` (or `(venue, date, amount)`), never merchant name alone; when a candidate's `transaction_id` already has a signal, LINK it instead of creating. Name-keyed tools — including `safe_taste_dedup.py`, which keys on `venue_name` — cannot catch this class. Same root-cause family as truncation-variant duplication, but the alias is in the source DB, not in Taste.
- **A Styx alias change re-emits an already-ingested purchase (confirmed 2026-09-26)** — When Plaid renames a merchant between syncs, the delta's `existing_items` check misses (the new alias string is absent) and `existing_signals` misses (the dedup_key is built from the new alias), so an already-ingested purchase is written again. Confirmed live: 13 duplicate Styx signal groups in one day — Hobee's (`HOBEES 3` → `Hobee's`), Stop & Shop (`Stop & Shop Square` → `Stop & Shop`), Island Brew Coffee, and 10 more — all re-written by a single delta run. **Detection:** `safe_taste_dedup.py --dry-run` surfaces them because the newer copy shares `(venue_name, date)`. Before applying, check the older copy's `item_id` still resolves; when it does, removing the newer copy loses no linkage. Symptom of an unresolved case: `styx_delta` reports items/signals created for a merchant you know is already in Taste.
- **The `scan-historical` date-bug fix was documented for months but never applied to the live script (repaired 2026-09-26)** — `references/scan_historical_date_bug.md` has prescribed `parsedate_to_datetime` since 2026-07-07, but `taste_scan.py` still carried the rigid `strptime('%a, %d %b %Y %H:%M:%S %z')` + `datetime.now()` fallback until 2026-09-26. It corrupts EVERY scan path, not just `scan-historical`: the 2026-09-26 16:46 batch stamped 144 email signals with the scan time, including 4 real orders dated 09-24/09-25. Measured on 6 real Gmail `Date` headers: the old format matches 3/6, `parsedate_to_datetime` matches 6/6 — the variants it rejects (`-0700 (PDT)`, `GMT`, non-padded day) are the common case. **Rule:** before trusting any scan's dates, grep the live script for the patched call, and test it against real header formats; a fix recorded in a reference doc is not a fix until it is in the running file.
- **Historical-scan cron jobs point at a non-existent script path (found 2026-09-26)** — The 365-day email and 365-day calendar backfill jobs invoke `/root/.hermes/skills/ocas-taste/scripts/taste_scan.py`, which does not exist; the live script is `/root/.hermes/profiles/indigo/skills/ocas-taste/scripts/taste_scan.py` (see `references/script_inventory.md`). Both jobs therefore fail every run, which is why a data-corrupting bug went unnoticed for months. **Do not fix the path alone** — that re-enables two 365-day backfills against a dataset that needs dedup and a date fix first; fix path, patch, and dedup strategy together.
- **Styx delta works without Google OAuth** — The Styx→Taste delta ingestion uses GOOGLE_PLACES_API_KEY (env var), not OAuth tokens. It runs successfully even when email/calendar auth is broken. Confirmed 2026-05-30: 124 venues enriched, 188 signals created, $8,174 tracked — all while OAuth token was 0 bytes.
- **Styx merchant names are truncated; Places handles it** — Styx truncates merchant names to ~15 characters. Google Places fuzzy text search resolves these correctly — tested at 100% match rate (124/124). Use `{merchant_name} restaurant` as the query, take the first result. See `references/styx_delta.md`.
- **Styx truncation creates duplicate items** — The enrichment pipeline creates separate items for each truncated Styx variant instead of canonicalizing via Google Places. This results in duplicate items (e.g., Milos split across 3 items, Kasa Indian Eatery across 5). The dedup in `styx_delta.md` Step 2 only checks `name.lower().strip()` (raw Styx name), not Places canonical name/address. **Fix:** Batch Places search first, group by `place_id`, create ONE ItemRecord per canonical venue. See `references/styx_truncation_fix.md`. **Cleanup:** merge variants by canonical `place_id` following the recipe in `references/styx_truncation_fix.md` — no one-shot cleanup script ships with this skill; do it inline (back up both JSONL files first). `styx_delta_corrected.py` self-heals orphans on the daily run.
- **Styx delta creates `place_id`-sibling duplicates if dedup checks name only (incident 2026-07-15)** — Near-name venues already in Taste ("Taco Bell" vs "Taco Bell Cantina", "Sidewalk Juice" SF vs "Sidewalk Juice- San Mateo") share one Google `place_id`. If the pre-check compares `name`/`item_id` instead of `place_id`, the ingestion writes duplicate items + signals and still reports "success". **Rule:** dedup by canonical `place_id`; LINK the signal when the place exists; create exactly one item otherwise. **Verification is mandatory and separate from the ingestion return** — run `scripts/verify_taste_delta.py` (asserts zero `place_id` collisions, zero `item_id` dupes, zero orphaned signals, zero `(merchant,date)` styx dupes). Reconciliation recipe: `references/styx_delta_placeid_dedup.md`. Note this is a DIFFERENT shape from truncation-variant duplication (different Styx names → same place), which the manual merge recipe handles and a name-only check will not catch.
- **Signal-item linkage is broken** — Styx-sourced signals have `item_id=None`. They use `venue_name` (raw truncated Styx name) not `item_id` for linkage to items. The item-signal graph is broken: recommendations can't properly aggregate signal strength per venue. After creating canonical items, signals must be updated to set `item_id` to the canonical item_id. See `references/styx_truncation_fix.md`.
- **execute_code is blocked in cron mode** — Cron jobs run without a user present to approve `execute_code`. Use `terminal()` with heredoc (`python3 << 'PYEOF'`) for inline Python, or invoke standalone scripts via `terminal()` / `skill_manage(action='write_file')`.
- **Legacy data path is stale** — An old data path may exist but is STALE. Active data is ONLY under `{agent_root}/commons/data/ocas-taste/`. Scripts referencing the old path will read outdated data.
- **Dedup key includes service + venue + date** — The cross-calendar dedup key is `{service}:{normalized_venue}:{event_date[:10]}`. Two extractions from different sources for the same venue on the same day are correctly deduplicated, but the same venue on different dates creates separate signals.
- **Enrichment script dedup uses `venue_name`, not `name`** — The enrichment pipeline's dedup check looks at `venue_name`, not the generic `name` field. Verify dedup logic when modifying the item schema.
- **Calendar scan enumerates writable calendars** — The scan calls `calendarList().list()` and filters for `accessRole in ('owner', 'writer')`, not just `primary`. Some consumption signals may come from shared or secondary calendars the user didn't expect.
- **Calendar scan can silently succeed with wrong account's data** — When the operator's token is empty and the script falls back to the agent's credentials, the calendar scan may still "succeed" if the agent has access to the same shared calendars (Personal, Family via email delegation). The scan report looks normal (events processed, signals created) but the data flows through the wrong OAuth client. Gmail scans fail visibly; calendar scans can mask the problem. Always verify the authenticated account in scan output — the `Initialized Gmail and Calendar with <file>` line shows which account was actually used.
- **`scan-calendar` output `signals_created` conflates Styx delta with calendar signals** — The JSON output's `signals_created` field reports the count from the Styx delta step, **not** the calendar promotion step. Calendar signals are promoted to the root `signals.jsonl` via `_process_extractions()` but the output number reflects Styx purchases. To find actual calendar signal count, query `signals.jsonl` for `extraction_source == 'calendar'`. See `references/storage_layout.md` for the two-store architecture.
- **`scan-calendar` is calendar-only — NOT the full pipeline** — `taste_scan.py scan-calendar N` only scans Google Calendar. It does NOT run Styx delta or email scan. Its `signals_created` output field correctly reflects only calendar signals (unlike the `taste:scan` cron job which chains calendar + Styx delta and reports Styx's count). For calendar-only historical backfill, use `scan-calendar 365`. For the full pipeline, use `taste_full_enrich.py`.
- **`scan-historical` DATE BUG — stamps every signal with the scan time (CRITICAL)** — `_extract_from_email` parses the email `Date` header with one rigid `strptime("%a, %d %b %Y %H:%M:%S %z")` and falls back to `datetime.now()` on ANY parse failure. In practice the fallback fires for the vast majority of emails (their `Date` headers don't match that exact format), so all emitted signals get `event_date` = the scan timestamp, NOT the real consumption date. Confirmed 2026-07-07: a 365-day run produced 137/141 signals dated `2026-07-07T09:06:23.xxx` (microsecond-spaced = the loop time). This **maximizes recency bias** — the opposite of the goal — and corrupts the model's temporal decay. **Do NOT run `scan-historical` for historical coverage until the parse is patched:** replace the strptime with `email.utils.parsedate_to_datetime()`. No bundled backfill script ships with this skill — patch first, scan second, then dedup with `safe_taste_dedup.py`. See `references/scan_historical_date_bug.md`.
- **`scan-historical` is email-only — NOT the full pipeline** — `taste_scan.py scan-historical N` only scans Gmail. It does NOT run Styx delta or enrichment. For the full pipeline (Styx delta + enrichment of unenriched items), use `taste_full_enrich.py` instead. The daily `taste:scan` cron (13:12) runs email/calendar scan then delegates to `taste_full_enrich.py` for Styx delta + enrichment. If OAuth is broken, `scan-historical` fails entirely but `taste_full_enrich.py` still works.
- **`scan-historical` output is NOT dedupable by a strict-key dedup** — A strict-key dedup reads `name`/`normalized_name`, but scan signals use `venue_name` and lack `name`/`normalized_name`, so all scan signals get an empty venue key and are silently skipped (false "0 dupes" on `--dry-run`). Combined with the date bug above, re-running `scan-historical` over an already-populated dataset silently pollutes it with un-dedupable, mis-dated signals. Use `safe_taste_dedup.py` (keys on `(venue_name, (event_date or date)[:10], extraction_source)`) and verify against the actual signal schema, not a tool's count.
- **`taste_scan.py status` and `data-quality` report 0 when run outside the venv** — Both commands use the `TasteSkill` class which resolves `data_dir` differently than the actual data location. Always run via the venv Python (`<hermes-home>/commons/data/ocas-taste/venv/bin/python3`) and verify the data path. For a quick count, use `wc -l signals.jsonl items.jsonl` directly. The `data-quality` subcommand has the same bug as `status` — it is NOT documented in `--help` but it exists and returns 0 for all counts when run outside the venv.
- **`taste_full_enrich.py` schema drift — prefer inline enrichment** — The script at `<hermes-home>/profiles/indigo/skills/ocas-taste/scripts/taste_full_enrich.py` generates `item_id` as `item-{safe_name}` (not UUID), uses `strength` field (not `signal_type`), and produces signals with `source: 'enrichment'` that lack the full schema from `references/styx_delta.md`. Items created by this script have `domain: 'restaurant'` instead of `'food'`. **Preferred approach for cron:** write inline Python via `terminal()` that calls Places API directly via `urllib.request` and writes properly structured records. Confirmed 100% enrichment rate with inline approach (2026-06-16, 36/36 transactions).
- **`taste_scan.py` default `data_dir` was the literal `<hermes-home>` placeholder (NOT fixed until 2026-07-26)** — The constructor default `Path("<hermes-home>/commons/data/ocas-taste")` was still present and never resolved (the "Path.home() already fixed on line 30" note was WRONG — the file literally contained the placeholder string). Symptom: scan initializes Gmail/Calendar fine, then crashes at `_save_config()` / `FileNotFoundError: '<hermes-home>/commons/data/ocas-taste/config.json'`. **Fix applied 2026-07-26:** the constructor now resolves `os.environ.get("AGENT_ROOT", "$AGENT_ROOT")` + `commons/data/ocas-taste` when no `data_dir` is passed. If you see the literal `<hermes-home>` path in a traceback, re-apply that patch. The SAME placeholder defect lives in `verify_taste_delta.py` (its default `DATA = "<hermes-home>/commons/data/ocas-taste"`) — it only runs if you pass `--data-dir <real-path>`. `dispatch_taste_dedup.py` had the same bug (fixed 2026-07-26, see its gotcha below).
- **`email_scan.py` and `run_historical_scans.py` auth-import hardening (2026-09-24)** — Both scripts previously imported the shared `google_auth` helper at module scope, which broke `--help` (and any other flag) on machines without the Hermes tree. **Fixed:** the import is now lazy inside a `_google_auth()` / `_auth()` helper that resolves via `AGENT_ROOT/scripts` and exits 3 with a clear message when the helper is absent. If you see `ModuleNotFoundError: google_auth` from either script, re-apply that lazy-import pattern — never move the import back to module scope.

It exits 0 with `VERIFY PASSED` on success; non-zero on any integrity violation. A "N created" return from the delta script is testimony, not proof — this verify step is the proof.

If that key (or the file) is missing, the service loop iterates zero services → `services_scanned: []`, `signals_created: 0`, and the only trace is a missing `config.json`. **Contract:** `config.json` MUST exist with an `email_sources` block (see `references/email_extraction.md` for the 8-service allowlist shape). - **Token expiry timezone suffix breaks `from_authorized_user_file()`** — Google OAuth token files may contain `expiry: "2026-06-17T17:41:40+00:00"` (ISO 8601 with timezone). The `google.oauth2.credentials.Credentials.from_authorized_user_file()` parser uses `strptime` with `%Y-%m-%dT%H:%M:%S` and fails with "unconverted data remains: +00:00". **Diagnosis:** Check `expiry` field format with `python3 -c "import json; d=json.load(open('<gworkspace-creds>/credentials/<email>.json')); print(repr(d.get('expiry')))"`. **Fix:** Strip the timezone suffix: `d['expiry'] = d['expiry'][:19]` and rewrite the file. The refreshed token will get a new `expiry` field that may or may not include the suffix depending on the OAuth library version. **Always check and fix the token expiry before running `taste_scan.py`** — the scan will fail silently or produce 0 results if the token can't be loaded. Also check for float expiry values (see next gotcha).
- **Token expiry stored as float instead of string** — Some token files store `expiry` as a Unix timestamp float (e.g., `1782328557.213807`) instead of an ISO string. The Taste script calls `.rstrip()` on this and crashes with `AttributeError: 'float' object has no attribute 'rstrip'`. **Fix:** Replace with ISO string: `d['expiry'] = time.strftime('%Y-%m-%dT%H:%M:%S', time.localtime(time.time() + 3600))`. See `references/token-repair.md` for the combined repair script.
- **Google Places enrichment is double-blocked (2026-09-26)** — `styx_delta_corrected.py` reported `ENRICHMENT: ok=0 failed=46`. Both endpoints are hard-blocked and the script swallows the reason (`except: return None`): (a) legacy `maps.googleapis.com/…/place/textsearch` returns `REQUEST_DENIED` — "You must enable Billing on the Google Cloud Project" — so the 100%-match-rate claim in the older notes is stale; (b) v1 `places:searchText` returns `HTTP 429 RESOURCE_EXHAUSTED` — `SearchTextRequest per day` quota exhausted for `project_number:628032148246`. **Never report a Styx delta as enriched on the strength of the script's return; check the `ENRICHMENT: ok=` line, and treat `ok=0` as a billing/quota blocker to report, not as "no new venues."** Once a key or project is fixed, re-enrich the backlog rather than re-running the delta (the signals are already written).
- **Two duplicate classes survive every name-keyed dedup, and one of them hides from `verify_taste_delta.py` (confirmed 2026-09-28)** — After a full cleanup the store still held 250 redundant Styx signals. (a) *Shared `signal_id`*: one Plaid `transaction_id` linked to two merchant aliases produces two signals sharing a `signal_id` (e.g. `styx:philz:2026-06-11` and `styx:philz coffee:2026-06-11`, both `sig-styx-b33Jo3Q...`). `safe_taste_dedup.py` keys on `venue_name` so it never sees them. (b) *Receipt-schema ghosts*: the 2026-09-24 batch wrote ~129 signals with `amount: null` and the real figure in `metadata.amount`, each duplicating a purchase already ingested. Because the top-level amount is null, **grouping on amount reports every ghost group as "distinct amounts" — they are invisible to amount-based dedup** — and `verify_taste_delta.py` reported only 22 of the 250. **The only reliable key is `metadata.transaction_id`.** Any repair must (1) read `amount` with a `metadata.amount` fallback, and (2) collapse a group only when a shared `transaction_id` proves one purchase. **Rule:** after any Styx delta, compare the signal multiset against the `transactions.db` multiset of `(normalized merchant, date, amount)` and resolve every surplus by `transaction_id` — never by name, never by amount alone.
- **A same-merchant same-day group with differing amounts is a real multi-visit day, never a duplicate (confirmed 2026-09-28)** — e.g. Down To Earth 2026-08-05 = 4 genuine charges ($45.88, $15.69, $1.41, $28.78), Philz 2026-03-23 = 3, Safeway 2026-09-16 = 2. 34 such groups are correct data. `verify_taste_delta.py` exits 1 on all of them because it keys on `(merchant, date)` with no amount awareness — **its non-zero exit is expected here and is not a repair target.** Fix the checker (amount- or `transaction_id`-aware) rather than deleting signals; a blanket dedup at this point destroys real visits.
- **Cron duplication guard: check the executions table before a scheduled scan re-runs its own pipeline (2026-09-28)** — the 13:12 `taste:scan` had already completed at 13:16:52 while a second invocation of the same job was starting; re-running the email/calendar scan would have double-written. `executions.db` in the profile's `cron/` dir holds `job_id, status, claimed_at, finished_at`; `cron/output/<job_id>/` holds each run's transcript. **Rule:** at the start of a scan cron, look up this job's own `job_id` and check whether today's occurrence already finished; if so, verify its claims against the data files and report instead of re-running the write path.
- **`verify_taste_delta.py` false `(None, None)` dupe on legacy styx signals** — 306 styx signals written by older runs carry venue/date only inside `dedup_key` (`styx:{name}:{date}`), not in `merchant_name`/`date`. The check keyed on the fields directly, so all 306 collapsed into a single bogus `(None, None)` dupe and masked the real violations behind it. Fixed by adding a `_mkey()` fallback that parses `dedup_key` — re-apply that patch if the script is ever reverted. **Only trust a `(None, None)` entry if the signals genuinely lack `dedup_key` too.**
- **`transaction_id` is NOT a usable dedup key in Styx (confirmed 2026-10-01)** — Plaid `transaction_id` values share a long common prefix: 39 unrelated transactions in styx.db all begin `8990J9ZDKgU6y8...`. They are distinct ids that merely share a prefix, so any equality check is technically valid but only 51 of 1597 signals carry a `transaction_id` at all (legacy signals key on name+date via `dedup_key`). Keying "new transaction" detection on it reports **668 false-new rows** against a true count of 3. **Rule:** detect genuinely-new Styx rows by `dedup_key == f"styx:{normalized_merchant}:{date}"` OR `(normalized merchant, date)` — the key the store actually uses — and treat `transaction_id` as a tiebreaker only, never as the primary key. The existing reference text calling `metadata.transaction_id` "the only reliable key" is wrong on this data.
- **`transaction_id` grouping surfaces legitimate cross-source pairs, not duplicates (confirmed 2026-10-01)** — 5 transaction groups hold 2 signals each; all 5 are a venue-level `signal_type: fine_dining` signal and a `purchase` signal describing the SAME real charge (e.g. DoorDash $64.11 = Little Star Pizza, Starbucks $35.00 = Starbucks Coffee Company). These are Plaid merchant aliases for one purchase, both correctly recorded. **Do not collapse a group on transaction_id alone** — collapse only when signal types are homogeneous AND amounts match.
- **`safe_taste_dedup.py` can orphan items when duplicate ITEMS exist (confirmed 2026-10-01)** — the store holds **266 duplicate-item groups (427 extra copies)** by normalized name (Golden Era ×7, Ike's Love & Sandwiches ×7, Philz Coffee ×5) with distinct `item_id`s, and **1194 of 1852 items have zero linked signals**. `safe_taste_dedup.py` keys on `venue_name`, so it cannot see duplicate items and will happily remove a signal whose `item_id` is the ONLY thing keeping a duplicate item alive. On today's dry run 31 of 36 target groups had divergent item linkage — applying it would have orphaned those items, and 3 further groups have differing amounts (real multi-visit: Atlas Cafe, Safeway, Vitamin Shoppe). **Rule:** before applying this script, group by `(venue,date,source)`, then check that the retained copy's `item_id` resolves in `items.jsonl` and that no surplus copy carries a different `item_id`. Fix duplicate items FIRST (canonicalize by name/`place_id`, merge signals), then dedup signals.
- **`scan-historical` creates signals in two schemas** — The email extraction produces signals with `signal_id`, `venue_name`, `extraction_source` (old schema). The enrichment pipeline that runs alongside produces signals with `name`, `source: "enrichment"`, `visit_count`, `strength` (new schema) — no `signal_id`, no `item_id`, no `extraction_source`. The two schemas coexist in `signals.jsonl`. The enrichment-schema signals may have duplicate venue names within a single scan run. This is a known issue; the enrichment pipeline should be deduplicated against existing signals before writing.
